The GameObject engine (`//engines:sgl-gameobject`, package `sgl.engine.gameobject`) arranges a
game as **objects** that carry **components**, **systems** that run in ordered **stages**, and
**scenes** that populate a **world**. It renders with OpenGL in 2D and 3D.

<Aside type="caution" title="Under active development">
This engine changes faster than the rest of SGL. `//engines/gameobject/examples/asteroids` is
always up to date and is the best reference.
</Aside>

To learn it by making a game, follow the [tutorials](/docs/tutorials/).

## The application

Extend `OpenGLGameObjectApp` and configure the game in `configure`. The engine owns `create`,
`frame`, `resize`, and `dispose`.

```scala
import sgl.engine.gameobject._
import sgl.engine.gameobject.render2d._
import sgl.engine.gameobject.spatial2d._

trait AbstractApp extends OpenGLGameObjectApp {
  override def configure(builder: GameBuilder): Unit =
    builder
      .install(UpdateCapabilitiesModule)        // drives Updatable components
      .install(Render2DModule)                  // draws sprites and tilemaps
      .setGlobal(ClearColor(0.02f, 0.02f, 0.05f, 1f))
      .setGlobal(FixedDeltaTime(1.0 / 60.0))
      .addSystem(Stage.PostUpdate, CollisionSystem)
      .setInitialScene(Level1)
}
```

Build it with an OpenGL backend rule such as `sgl_desktop_lwjgl_app`, `sgl_html5_opengl_app`, or
`sgl_desktop_native_app(backend_app = "NativeOpenGLApp")`. Add `@sgl//engines:sgl-gameobject` to
the core library's `deps`.

## Concepts

| Concept | What it is |
| --- | --- |
| `World` | Holds objects, scopes, component indexes, and the `Globals` |
| `GameObject` | An identity (`id`, `name`) with at most one component of each type |
| `TypedObject[Has]` | A `GameObject` whose type lists the components it has. `GameObject2D` is `TypedObject[Spatial2D]`. |
| `Component` | A plain class with an `owner`, stored and indexed by its concrete class |
| `Globals` | Values for the whole world, one per class, such as `DeltaTime`, `ClearColor`, and installed modules |
| `GameSystem` | Code that runs over the world once per stage |
| `GameModule` | A reusable bundle of systems and globals |
| `Scene` | Loads a set of objects. Its objects are destroyed when another scene loads. |
| `Scope` | Groups objects so they are destroyed together. Every object is created in one. |

## Objects and components

Objects are built as **typed objects**. A `TypedObject[Has]` wraps a `GameObject`, and its type
records the components that are known to be attached. Each `attach` returns the same object with a
larger type, so an object is composed as a chain:

```scala
context.spawn("Enemy")               // TypedObject[Any]
  .attach(new Health(_, points = 3))       // TypedObject[Health]
  .attach(new EnemyBrain(_))               // TypedObject[Health & EnemyBrain]
```

`GameObject2D` and `GameObject3D` are aliases of `TypedObject[Spatial2D]` and
`TypedObject[Spatial3D]`. `context.spawn2D` returns an object that already has its spatial.
There is one kind of composed object and one `attach`.

A component is an ordinary class with methods and private state. It takes the typed object as its
constructor parameter and extends `ComponentOf(obj)`, which derives its `owner` and keeps the
object reachable as `obj`:

```scala
final class Health(obj: TypedObject[Any], var points: Int) extends ComponentOf(obj)
```

Components are stored and indexed by their class, so no key or registration is needed. An object
carries at most one component of each class, and a component is attached under its own concrete
class: attaching a subclass instance as its parent type throws a `CompositionError`.

`TypedObject[Any]` means that the component works on any object. Components written with a plain
`owner: GameObject` parameter, such as `new Lifetime(_, 1.2)`, are attached with `attachPlain`.

Override `onDestroy()` to release what a component holds on other objects. It is called while the
owner and its siblings are still attached.

## Composition checked by the compiler

A component that needs other components on its object asks for them in the type of its constructor
parameter, and reads them with `get`, which the type guarantees to succeed:

```scala
final class Collider(obj: GameObject2D, var radius: Float) extends ComponentOf(obj) {
  private val spatial = obj.spatial

  def overlaps(other: Collider): Boolean = {
    val d = spatial.global.position - other.spatial.global.position
    val reach = radius + other.radius
    d.x * d.x + d.y * d.y <= reach * reach
  }
}

final class Bullet(obj: TypedObject[Collider]) extends ComponentOf(obj) {
  val collider: Collider = obj.get[Collider]
}

final class Player(obj: TypedObject[Spatial2D & Velocity & Collider]) extends ComponentOf(obj) with Updatable {
  private val velocity = obj.get[Velocity]
  // ...
}
```

```scala
context.spawn2D("Bullet", Transform2D(position = pos))   // GameObject2D
  .attach(new Collider(_, 4f))                                   // & Collider
  .attach(new Bullet(_))                                         // & Bullet
  .attach(new SpriteRenderer(_, SpriteVisual.Circle(Color(1f, 0.9f, 0.5f, 1f)), 7f, 7f))
```

The compiler rejects these mistakes:

- Attaching `Bullet` before `Collider`: *"This object is not known to have a Collider"*.
- Attaching a `SpriteRenderer` or a `Collider` to an object without a `Spatial2D`.
- Attaching a second `Collider`: *"This object already has a Collider"*.

A component built from another object's handle has the wrong owner and is rejected when it is
attached. `TypedObject` holds only the `GameObject` and adds no runtime state. Its type stays
accurate because components are never detached from a live object.

The engine's own components follow the same rule. `SpriteRenderer` and `Tilemap` take a
`GameObject2D`, and `MeshRenderer` and `Camera3D` take a `GameObject3D`. `Camera2D`, `TextOverlay`,
and `CircleMaskTransition` take a `TypedObject[Any]`.

### Dynamic lookup

Systems and debugging code can still look components up at runtime:

```scala
obj.component[Health]        // Option[Health]
obj.require[Health]          // Health, or a CompositionError
obj.destroy()
```

### Requirements on the world

Some requirements are not properties of the object but of the world, typically a module that must
be installed for the component to do anything. A trait states them once by mixing in
`RequiresGlobals`, and they are checked whenever a component with that trait is attached:

```scala
trait Updatable extends RequiresGlobals {
  def update(context: GameContext)(using Scope): Unit

  override def requiredGlobals: Vector[Class[?]] =
    super.requiredGlobals :+ Globals.keyOf[UpdateCapabilitiesModule.type]
}
```

This is how every `Updatable` requires `UpdateCapabilitiesModule`, so you cannot attach one that
would never be updated. Overrides add to `super`, because a component can mix in several such
traits.

### Domain objects

A typed object can be passed around as a domain object. Systems usually iterate over a component
that holds what they need:

```scala
context.world.index[Bullet].foreach { bullet =>
  if(bullet.collider.overlaps(target)) bullet.destroy()
}
```

`foreach` and `iterator` on an index never return a component whose object was destroyed, even one
destroyed earlier in the same traversal. Components attached during a traversal appear in the next
one. `toVector` is a plain snapshot, so code that keeps it checks `isAlive` itself.

An index is asked for by the component's own class. Asking for a trait or a base class of attached
components throws a `CompositionError` instead of returning an empty index; `obj.component[A]`,
`obj.require[A]`, and `get[A]` behave the same way.

`destroy()`, `isAlive`, `component`, and `require` work on anything with a `HasGameObject` instance:
`GameObject`, `TypedObject` (including `GameObject2D` and `GameObject3D`), and every component.
Give your own classes an instance in their companion:

```scala
final class Ship(val obj: GameObject2D, val hull: Collider)
object Ship {
  given HasGameObject[Ship] with {
    def gameObjectOf(ship: Ship): GameObject = ship.obj.gameObject
  }
}
```

## Systems and stages

A system has a stable `SystemId` and runs once per frame in its stage. Query components through
the world's indexes:

```scala
object CollisionSystem extends GameSystem {
  override val id: SystemId = SystemId("game.collision")

  override def run(context: GameContext)(using Scope): Unit = {
    val asteroids = context.world.index[Asteroid]
    context.world.index[Bullet].foreach { bullet =>
      // An asteroid destroyed by one bullet is skipped for the next ones.
      asteroids.iterator.find(a => bullet.collider.overlaps(a.collider)).foreach { asteroid =>
        bullet.destroy()
        asteroid.destroy()
      }
    }
  }
}
```

Each frame runs these stages in order. `FixedUpdate` runs zero or more times so that it advances
in steps of `FixedDeltaTime` (default 1/60 s):

<Steps>

1. `PreUpdate`
2. `FixedUpdate`, with `DeltaTime` set to the fixed step
3. `Update`
4. `PostUpdate`
5. `PreRender`
6. `Render`, inside the frame: the screen is cleared before it and the frame is presented after it

</Steps>

`Startup` runs once before the initial scene loads. `context.dt` is the frame's delta time in
seconds as a `Float`; the `DeltaTime` and `ElapsedTime` globals hold the same as `Double`s. A
schedule rejects duplicate system IDs.

A frame runs at most `maxStepsPerFrame` fixed steps (8 by default, set with
`FixedDeltaTime(1.0 / 60.0, maxStepsPerFrame = 4)`) and drops the time beyond that, so a long
frame slows the simulation down for a moment instead of replaying every missed step. The frame's
own delta time is capped too, by the `MaxDeltaTime` global (0.25 s by default): a longer frame is
seen by the game as that long.

Two more stages run outside of a frame: `Pause` when the application leaves the foreground and
`Resume` when it comes back, which is where a game saves its state or stops its music. The current
scene is told first, through its `pause` and `resume` methods. Fixed
steps start over on resume, so the time spent in the background is not simulated.

For small systems, `GameSystem("game.spawner") { ... }` creates one from a block that receives a given
`GameContext` and a given `Scope`, so it can spawn objects directly.

### Order within a stage

The systems of a stage run in the order they are added, which follows the order modules are
installed in. A system that depends on another one says so when it is added, instead of relying on
that order:

```scala
builder.addSystem(Stage.Update, CameraFollowSystem, after = Set(UpdateComponentsSystem))
```

`after` and `before` take systems of the same stage, so keep a `GameSystem("...") { ... }` in a `val`
if others are ordered against it. Systems without constraints keep
the order they were added in. A system that is not installed is ignored, so you can order against
an optional module. Building the game throws a `CompositionError` when the constraints form a
cycle, or when they name a system that is only in another stage.

### Systems of a scene

Systems added to the builder run in every scene. A scene adds its own when it loads, and they go
away with it:

```scala
object Level extends Scene {
  override def load(context: GameContext)(using Scope): Unit = {
    context.addSystem(Stage.Update, EnemySystem)
    context.addSystem(Stage.Update, InputSystem, before = Set(EnemySystem))
  }
}
```

They are ordered together with the builder's systems, and the same mistakes throw a
`CompositionError` from `addSystem`. A system runs with the scope it was added in, so what it
creates goes away with that scope too. One added while its stage is running starts the next time
the stage runs.

A scene can install a whole module the same way, with `context.install(module)`. Its systems and
globals last as long as the scene. A module that is already installed in the game, or in that
scope, is left as it is. Installing one that belongs to another scope throws a `CompositionError`,
and so does a module with a `Startup` system.

### Pausing systems

`addSystem` takes a condition, asked just before each run. The system is skipped while it is false:

```scala
final class Paused(var on: Boolean = false)

builder
  .setGlobal(new Paused)
  .addSystem(Stage.Update, EnemySystem, when = !_.global[Paused].on)
  .addSystem(Stage.Update, PauseMenuSystem)
```

`Updatable` components are all driven by one system, so one that should pause checks in its
`update`. A skipped system also skips what it draws: leave the ones in `Render` running.

### Per-object updates

Behavior that is specific to one object can implement `Updatable` or `FixedUpdatable` instead of
having a system. Only components that implement these traits are indexed and updated:

```scala
final class Lifetime(override val owner: GameObject, var seconds: Double) extends Component with Updatable {
  override def update(context: GameContext)(using Scope): Unit = {
    seconds -= context.dt
    if(seconds <= 0.0) this.destroy()
  }
}
```

Prefer systems for logic that applies to many objects.

## Globals and modules

`world.globals` holds values for the whole world. A value is stored under the class it is set as, so
there is one value per class and no key to declare:

```scala
final case class Difficulty(level: Int)

builder.setGlobal(Difficulty(2))
context.global[Difficulty]
world.globals.getOption[Difficulty]  // also get, set, contains
```

Type arguments are not part of the class: wrap a `List[Int]` in a class of its own instead of
storing it directly.

A global set this way lives as long as the world. For state that belongs to one scene, set it from
the scene with `context.setGlobal(value)`: it is bound to the scene's scope and goes away with it,
giving back the value it replaced if there was one.

```scala
object Level1 extends Scene {
  override def load(context: GameContext)(using Scope): Unit = {
    context.setGlobal(LevelState(lives = 3))   // gone when another scene loads
  }
}
```

A single component found with `world.single[A]` is the other way to hold scene state. Use a
global for a plain value, and a component when the state belongs to an object.

A `GameModule` bundles globals and systems. The built-in `UpdateCapabilitiesModule`
publishes itself among the globals, which is what `Updatable` and `FixedUpdatable` require.

Drawing is done by modules too, with systems in the `Render` stage. `Render2DModule` draws sprites
and tilemaps ordered by `z`; `Render3DModule` draws meshes from the active `Camera3D`. Install the ones a game uses: the 2D and 3D components require their
module, so attaching a `SpriteRenderer` without `Render2DModule` throws a `CompositionError`
instead of leaving an object that never appears.

## Scenes and scopes

A scene populates the world. Each loaded scene gets its own scope, and its objects are destroyed
when another scene loads:

```scala
object Level1 extends Scene {
  override def load(context: GameContext)(using Scope): Unit = {
    context.spawn2D("Camera").attach(new Camera2D(_, Vec2(800f, 600f), priority = 10))
    // ...
  }

  override def unload(context: GameContext)(using Scope): Unit = ()
}

context.runtime.loadScene(GameOver)   // applied after the current frame renders
```

Creating an object always names its scope. `GameContext` helpers use the current scene's scope.
`World` methods take a `using Scope` with no default, so a helper called from a scene declares one:

```scala
def spawnAsteroid(world: World, i: Int)(using Scope): Unit =
  world.spawn2D(s"Asteroid-$i").attach(...)
```

Forgetting the `(using Scope)` is a compile error, not an object that silently survives scene
changes. Outside scenes and systems, pass a scope explicitly or write `import world.given` to use
the world's global scope, whose objects persist across scenes. Use `world.createScope` and
`world.destroyScope` for smaller groups.

Find singletons with `world.single[A]` and `world.requireSingle[A]`. Both throw a
`CompositionError` when the world holds more than one `A`.

### Scenes that load first

A scene that needs files or images before it can be populated extends `AsyncScene[A]`, where `A` is
what it loads. `preload` starts the loading and returns one `Loader[A]`; when it has completed,
`load` is called with the result:

```scala
final case class LevelAssets(map: Array[String], tiles: Texture2D)

object Level extends AsyncScene[LevelAssets] {
  override def preload(context: GameContext)(using Scope): Loader[LevelAssets] = {
    val renderer = context.engine.renderer
    for {
      map <- System.loadText(Assets.text.level)
      tiles <- renderer.whenReady(renderer.loadTexture2D(Assets.rawImage.tiles))
    } yield LevelAssets(map, tiles)
  }

  override def load(context: GameContext, assets: LevelAssets)(using Scope): Unit = {
    // spawn the level from assets.map, with assets.tiles already usable
  }
}

context.runtime.loadScene(Level)                                       // the current scene stays until Level is ready
context.runtime.loadScene(Level, whileLoading = Some(LoadingScreen))   // or show another scene meanwhile
```

- The scene that was running keeps running until the new one is ready, and the swap happens
  between two frames. The `SceneLoading` global is present in the meantime.
- Pass each loading to `context.track(loader)` in `preload`, and a loading screen can show
  `context.global[SceneLoading].progress`, from 0 to 1. It counts loadings, not bytes. Start and
  track them all before combining them: in `for { a <- track(...); b <- track(...) }` the second
  only starts after the first, and the progress steps back.
- `preload` is given the scope of the new scene. The textures and meshes it creates are released
  with the scene, or at once if the loading fails or another scene is requested first.
- `preload` cannot create objects: that throws a `CompositionError`. Objects are created in `load`.
- If the loading fails, the current scene stays and the failure is thrown out of the frame. Pass
  `onFailure = cause => ...` to `loadScene` to handle it instead.
- What `preload` produced and its scope does not own, such as a music, is given back in
  `release(assets)`. It is called once for each loading that succeeds, even if the scene was
  abandoned before it appeared.
- `renderer.whenReady(texture)` completes when a texture's image is loaded, and fails if it could
  not be.

`builder.setInitialScene` takes an `AsyncScene` too.

### Acting on something loaded later

To use something that arrives while a scene is already running, pass its `Loader` to
`context.whenLoaded`:

```scala
context.whenLoaded(Audio.loadMusic(Assets.audio.theme), release = _.dispose()) { music =>
  music.play()
}
```

With `release`, the scope owns what was loaded: it is released when the scope is destroyed, or as
soon as it arrives if the scope is already gone.

The block runs on the game thread at the start of a frame, and only if the scene that asked is
still the current one. Do not create objects from `loader.foreach` or `loader.onLoad`: on some
backends those callbacks run on a loading thread, and they still run after the scene is gone.

## 2D

`spatial2d` adds `Spatial2D` (a local `Transform2D` of position, rotation, and scale, with parent
and children) and `GameObject2D`. Extensions on `GameObject2D` give direct access to `spatial`,
`local`, `global`, `parent`, `children`, `setParent`, `clearParent`, `childOf`, and
`transformPoint`. They are defined in the `Spatial2D` companion, so they need no import.
`childOf` sets the parent and returns the object, so it fits in a chain:

```scala
val ship = context.spawn2D("Ship")
  .attach(new SpriteRenderer(_, SpriteVisual.Triangle(Color(0.9f, 0.9f, 1f, 1f)), 28f, 34f))

context.spawn2D("Thruster", Transform2D(position = Vec2(0f, 20f)))
  .childOf(ship)
  .attach(new SpriteRenderer(_, SpriteVisual.Circle(Color(1f, 0.5f, 0.2f, 1f)), 8f, 8f))
```

`obj.spatial.local` is writable. `obj.global` is computed from the parent chain when it is read, so
it is never stale and does not depend on system order. For hierarchies with non-uniform scale, use
`transformPoint`, which keeps affine shear that the decomposed `global` transform cannot represent.

A child belongs to its parent: destroying an object destroys everything below it, whatever scope
the children were created in. To keep a child, take it out first with `clearParent()` or give it
another parent.

The parent and child links come from the `Hierarchy` trait, which `Spatial2D` and `Spatial3D` mix
in. A game can mix it into its own components for any other tree of objects.

Render components:

| Component | Draws |
| --- | --- |
| `SpriteRenderer` | `SpriteVisual.Texture`, `Triangle`, or `Circle` at a size and `z` |
| `Tilemap` | A batch of `TileQuad`s, typically from a Tiled map |
| `Camera2D` | The view. The active camera with the highest `priority` wins. |

The `extras` package has two more, each with its own module to install:

| Component | Module | Draws |
| --- | --- | --- |
| `TextOverlay` | `TextOverlayModule` | Screen-space lines of text with a background |
| `CircleMaskTransition` | `CircleMaskModule` | A circular wipe for scene transitions |

### Drawing your own components

A game draws its own components the same way the engine draws sprites: a system in the `Render`
stage submits drawings to `Render2D`. Nothing is drawn until the stage has ended, when the frame is
composed from everything submitted, so what ends up in front depends on `z`, never on which system
ran first.

```scala
final class Spark(obj: GameObject2D, var life: Float) extends ComponentOf(obj)

object SparkRenderSystem extends GameSystem {
  override val id: SystemId = SystemId("game.sparks")

  override def run(context: GameContext)(using Scope): Unit = {
    val draw = context.global[Render2D]
    context.world.index[Spark].foreach { spark =>
      draw.world(z = 5f) { painter =>
        val p = spark.global.position
        painter.quad(p + Vec2(-2f, -2f), p + Vec2(2f, -2f), p + Vec2(2f, 2f), p + Vec2(-2f, 2f),
          Color(1f, 0.8f, 0.2f, spark.life))
      }
    }
  }
}

builder.addSystem(Stage.Render, SparkRenderSystem)
```

`draw.world(z)` takes points in world units, seen through the active camera. `draw.screen(order)`
takes screen pixels from the top left and goes over every world drawing. The painter has
`triangle`, `quad`, and `image` for a textured quad, plus the `camera` position, the `viewport`
size, and the `screenSize`. `TextOverlay` and `CircleMaskTransition` are written this way and are
short examples to read.

Textures are loaded from typed assets through the renderer, usually while a scene loads:

```scala
val renderer = context.engine.renderer
val coin: Texture2D = renderer.loadTexture2D(Assets.drawable.coin)
context.whenLoaded(renderer.whenReady(coin)) { coin =>
  context.spawn2D("Coin").attach(new SpriteRenderer(_, SpriteVisual.Texture(coin), 32f, 32f))
}
```

A texture belongs to the scope it is loaded in. An image is uploaded once however many textures
show it, and leaves the GPU with the last of them. An image needed by several scenes in a row stays
loaded if it is also loaded in the world's global scope.

A scene that should appear with its textures already loaded waits for them in the `preload` of an
[`AsyncScene`](#scenes-that-load-first).

Drawables packed with [`sgl_texture_atlas`](/docs/assets/#texture-atlases) are drawn from shared
pages, and consecutive draws are batched, even across a few textures.

## 3D

`spatial3d` has `Spatial3D` (`Transform3D` with a quaternion rotation) and `GameObject3D`, with the
same extensions as in 2D, where `globalMatrix` replaces `global`.
`render3d` has `Camera3D` and `MeshRenderer`. A camera is placed by its object's transform, like a
mesh: it looks along its local -Z axis, and `Transform3D.lookAt(eye, target, up)` builds a
transform that faces a point. Create meshes, textures, and materials through the renderer. They
belong to the scope they are created in, so what a scene loads is released when the scene is
unloaded, with nothing to keep track of:

```scala
val renderer = context.engine.renderer
val sphere = renderer.createMesh(MeshPrimitives.sphere(32, 18))
val sunMaterial = renderer.createMaterial(renderer.loadTexture2D(Assets.rawImage.sun), emissive = 1f)
val earthMaterial = renderer.createMaterial(renderer.loadTexture2D(Assets.rawImage.earth), emissive = 0f)

val sun = context.spawn3D("Sun").attach(new MeshRenderer(_, sphere, sunMaterial))
val earth = context.spawn3D("Earth", Transform3D(position = Vec3(3.2f, 0f, 0f)))
  .attach(new MeshRenderer(_, sphere, earthMaterial))
earth.setParent(sun)
```

`renderer.loadTexture2D` returns a `Texture2D`, the same one sprites use, and a material takes any
of them, a drawable packed in an atlas included. Texture coordinates outside of 0 to 1 are clamped
to the edge of the image. `releaseMesh`, `releaseTexture`, and `releaseMaterial` free one before its scope ends,
and `scope.onDestroy(action)` registers anything else a scene needs to release.

### Drawing your own 3D components

`Render3D` is to 3D what `Render2D` is to 2D: a system in the `Render` stage submits drawings to
it, and they are drawn when the stage has ended, seen through the active `Camera3D`.

```scala
override def run(context: GameContext)(using Scope): Unit = {
  val draw = context.global[Render3D]
  context.world.index[Forest].foreach { forest =>
    // Many meshes without an object for each.
    forest.trees.foreach(tree => draw.mesh(forest.mesh, forest.material, tree))
  }
  context.world.index[Smoke].foreach { smoke =>
    val p = smoke.position
    // A quad that faces the camera.
    draw.painted(p) { painter =>
      val (r, u) = (painter.right * smoke.size, painter.up * smoke.size)
      painter.image(smoke.texture, p - r + u, p + r + u, p + r - u, p - r - u,
        color = Color(1f, 1f, 1f, smoke.opacity))
    }
  }
}
```

Meshes are drawn first and hide one another by depth. `draw.painted(at)` drawings follow, from the
farthest `at` to the closest, so they can be translucent; meshes in front of them hide them, and
they are not lit. All 2D drawings come last.

`//engines/gameobject/examples/solar-system` is a complete example.
